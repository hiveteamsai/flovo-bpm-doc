## 🔧 Değişenler / kararlar
- **UserGroup → `groupApprovalRequired` (bool):** Kullanıcı grubuna **grup onayı gerekli mi?** ayarı eklendi. Bir grup bir
  formu beklerken (`FormAwaitingUser.userGroupId`) bu `true` ise, onaylayan üyeler `UserGroupApprovedUser`'dan tespit edilir.
- **`delete` = soft-delete (runtime):** Runtime/işakışı modellerinde `delete` alanı **soft-delete** işaretidir (fiziksel
  silme yok); `delete` içeren tüm modellerde aynı kural. _(Not: organizasyon-ayarı master modelleri `deleted` alan adını
  kullanır; runtime tarafı görselle uyumlu `delete`.)_
- **`ProcessStepExecution` kesinleşti (🟢 TANIMLI):** alan anlamları netleşti — `executionDate` = adıma **ilk girildiği**
  tarih; **aksiyon tetiklendiğinde birlikte dolan alanlar**: `processStepActionId` (hangi aksiyon) · `atUserId`/`atApiKeyId`
  (tetikleyen) · `actionTriggerDate` · `processStepActionParameter` (**`ActionTransfer`** = `parameters`/`changeList`/`action`
  paketinin JSON kaydı) · `atDelegateUserId` (vekaleten onaylayan). **`formId` null** = yeni form oluşturmadan `formId`'si olan
  başka bir workflow'a yönlendiren adım (örn. `sampleProcess/scanBarcode` → `redirect`).
- **`FormAwaitingUser` kesinleşti (🟢 TANIMLI):** form üzerinde **aksiyon alabilecekleri** tutan tablo; bir form/adım için
  **n kayıt** olabilir. Senaryolar: **Kullanıcı** adımı → 1 kayıt (`userId`) · **Kullanıcı Grubu** adımı → 1 kayıt
  (`userGroupId`) · **çoklu seçim** (multi-select, gruba bağlı değil) → **n kayıt** (her biri `userId`). `userId` **veya**
  `userGroupId`'den biri dolu zorunlu. **Senkronizasyon:** Kullanıcı/Kullanıcı Grubu/Processing adımına gelince aksiyon
  alabilecekler **eklenir/silinir** (sync). Amaç: aksiyon alabilecekleri `ProcessStepExecution` filtrelemeden **doğrudan**
  bu tablodan tespit (maliyet).
- **`Form` form-düzeyinde kesinleşti (🟢 TANIMLI):** Form **FormCreator** süreç adımı tarafından oluşturulur; `createdDate` =
  FormCreator'ın formu oluşturduğu tarih. **Property value depolaması sonraya bırakıldı** (daha detaylı araştırma sonrası;
  alan-düzeyi tanımlar ayrı değer dokümantasyonunda) → `todo.md`'ye **Tier 1** açık sorusu eklendi.
- **`RelatedForm` kesinleşti (🟢 TANIMLI):** yön semantiği netleşti — **`relatedPropertyId`, `relatedFormId` id'li formun/
  servisinin içindeki** property'dir (ilişkiyi kuran Form List / Combobox) ve **`formId`**'deki formu işaret eder. Invariant:
  `Property(relatedPropertyId).serviceId == Form(relatedFormId).serviceId`. Örnek eklendi (masraf formu ↔ masraf: Form List;
  masraf ↔ seyahat: Combobox). Böylece **`models/workFlows/` 6 modelin tamamı 🟢 TANIMLI** oldu.

## ❓ Yeni açık sorular
- **`apiKeyId` içeriği/adı (Customer API kimliği)** — Customer API ile oluşturulan kayıtlarda oluşturan `User`
  olmadığından "kim yaptı"yı tutmak için `WorkFlow.createdByApiKeyId` / `ProcessStepExecution.atApiKeyId` var. Ad
  **geçici**; içeriği Customer API erişim mekanizması kesinleşince doğrulanacak. `todo.md`'ye eklendi; `WorkFlow` amacı
  bu doğrultuda kesinleştirildi (`createdByUserId` **veya** `createdByApiKeyId` — biri dolar).
- **Form validasyon durumu — `Form.validated` (bool) mü, `FormValidation` tablosu mu?** — Workflow'dan validasyonları sürekli
  tekrar yapmamak ve iş kuralı (`ApplyValidation`) validasyonlarıyla tutarsızlığı önlemek için. **Karar sonraya.**
  `todo.md` + `new-vs-current.md §14` + `form.md` açık notuna eklendi.
- **Webhook/Triggered süreç adımı türü (yeni)** — Workflow modelleri netleşince ortaya çıkan uyuşmazlık: Webhook bir
  **aksiyon** olarak modelli ama `ProcessStepExecution.processStepId` gerektiğinden, süreçten bağımsız child süreçte
  dışarıdan tetiklenen webhook bir adıma bağlı olmadığı için kayıt doğru atılamıyor. **Öneri:** yeni **Webhook/Triggered**
  adım türü; API ile *aksiyon* değil **bu adım** tetiklenir, webhook'u tutan aksiyon **`default`**'a dönüşüp bu adıma
  bağlanır. **Karar sonraya.** → `todo.md` + `process-step.md §4` açık sorusu; `sampleProcess/createPdfAsync` alt bilgisine
  ⚠️ not eklendi.
