2. Olası Mimari Yaklaşımlar

BPM tool için değerlendirilen tüm mimari yaklaşımlar, artıları, eksileri ve teknik detaylarıyla:

2.1. Modüler Monolit

Tek container içinde, modüler olarak yapılandırılmış uygulama. Modüller arası in-process iletişim, tek veritabanı.

✓ Artıları

  • Tek DB = en düşük maliyet (~$65/ay)
  • In-process çağrı = sıfır latency
  • Transaction bütünlüğü (ACID garanti)
  • Deploy basit (tek container)
  • 2-3 kişilik ekip yönetebilir
  • Debug/test çok kolay
  • İleride modül ayırma kolay (sınırlar hazır)

✗ Eksileri

  • Bir modül çökerse tüm app çöker
  • Ölçekleme granüler değil
  • Uzun süren işler (AI, export) main thread'i bloklar
  • Büyük ekiplerde merge conflict riski
  • Disiplin gevşerse spagetti olur

2.2. Full Microservices (Her Servise Ayrı DB)

Her iş alanı bağımsız bir servis. Kendi veritabanı, kendi container'ı, ağ üzerinden iletişim.

✓ Artıları

  • Her servis bağımsız deploy
  • Bir servis çökerse diğerleri çalışır
  • Bağımsız ölçekleme (sadece yoğun servisi scale et)
  • Her servis farklı teknoloji kullanabilir
  • Büyük ekipler için uygun

✗ Eksileri

  • 7+ ayrı DB = çok yüksek maliyet ($270-585/ay sadece DB)
  • Distributed transaction (Saga pattern) zorluğu
  • Service-to-service latency (her çağrı 5-20ms)
  • 2-3 kişi yönetemez (min 5+ kişi gerekir)
  • Debug/trace karmaşık (distributed tracing şart)
  • Data duplication ve eventual consistency

Not: Microservice + Tek DB = Anti-Pattern

Maliyet düşürmek için "microservice ama tek DB" düşünülebilir. Ancak bu, microservice'in operasyonel karmaşıklığını alıp, bağımsızlık avantajını kaybettirir. Connection pool tükenmesi, coupling, noisy neighbor sorunları yaratır. Tek DB kullanacaksanız zaten modüler monolit veya SOA daha mantıklıdır.

2.3. SOA — Self-Contained Systems

Microservice ile Monolit arasında. Az sayıda (2-4) büyük, kendi kendine yeten sistem. Her sistem içinde birden fazla modül, aralarında event-driven iletişim.

✓ Artıları

  • Sadece 2-3 system (10 microservice değil) — yönetilebilir
  • System içi: 0 latency (in-process). Workflow form+rule kontrolü anında.
  • Bağımsız deploy (AI deploy'u Core'u etkilemez)
  • DB sayısı makul (2 adet = ~$130/ay)
  • AI uzun süren işleri Core'u bloklamaz
  • BPM'de kritik olan transaction bütünlüğü korunur
  • İleride bir modülü ayrı system'e çıkarmak kolay

✗ Eksileri

  • Core sistem hala büyükçe (monolit'e benzer iç yapı)
  • Sistemler arası eventual consistency
  • Full microservice kadar granüler ölçekleme yok
  • 2 ayrı deployment pipeline yönetimi

SOA vs Microservice: Aynı Senaryo Karşılaştırması

"Kullanıcı form doldurdu → workflow ilerletildi → yetki kontrolü → bildirim gönderildi"

Microservice (6+ ağ çağrısı)
  • Client → Gateway → Form Service
  • Form Service → Workflow Service
  • Workflow → Rule Service
  • Workflow → Auth Service
  • Workflow → Notification Service
  • Her çağrı ~5-20ms
  • Toplam overhead: ~30-100ms
SOA (0 ağ çağrısı)
  • Client → Core BPM (tek çağrı)
  • Form module → function call (0ms)
  • Workflow module → function call (0ms)
  • Rule module → function call (0ms)
  • Auth module → function call (0ms)
  • Notify module → function call (0ms)
  • Toplam overhead: ~0ms

2.4. Event-Driven Architecture + Event Sourcing

"State'i DB'ye yaz" yerine her işlemi event olarak sakla. Güncel state event'lerin tekrarından türetilir. BPM'in doğasına çok uygun: bir iş akışı zaten "olayların sırası"dır.

✓ Artıları

  • Tam audit trail — compliance için kritik (KVKK, SOC2)
  • Geri alma — compensating event ile state düzeltme
  • Yazma çok hızlı (append-only, sadece INSERT)
  • AI için hazır veri kaynağı (event stream)
  • Temporal query ("3 gün önceki state neydi?")

✗ Eksileri

  • Öğrenme eğrisi yüksek (2-4 hafta ramp-up)
  • Event schema değişimlerini yönetmek zor (upcasting)
  • Projection güncellenmesi ~ms gecikebilir
  • Debug zorlaşabilir (state = event replay)
  • Tüm modüllere uygulamak overengineering (sadece workflow için ideal)

2.5. Hexagonal Architecture (Ports & Adapters)

Deployment modeli değil, iç tasarım prensibi. Core domain hiçbir teknolojiye (framework, DB, cloud) bağımlı olmaz. Dış bağımlılıklar adapter'lar üzerinden bağlanır.

Artısı: Test edilebilirlik mükemmel, teknoloji değişikliği core'u etkilemez, temiz kod yapısı.
Eksisi: Başta fazla interface/boilerplate, basit CRUD için overengineering olabilir.

2.6. Serverless-First (Mevcut Yapınız)

Tüm logic cloud function'larda. Şu an Azure Functions kullanıyorsunuz — bu yaklaşımın sınırlarını yaşıyorsunuz.

2.7. Cell-Based Architecture

Her "cell" bir müşteri grubu için tamamen izole deployment. Netflix/Amazon ölçeğinde platformlar için.

Artısı: Tam izolasyon, bir cell çökerse sadece o müşteriler etkilenir, GDPR compliance kolay.
Eksisi: Çok pahalı (her cell = tam stack kopyası), operasyonel yük çok yüksek.
Sonuç: Şu an overkill. 100+ enterprise müşteride tekrar değerlendirilebilir.

4.5. Bu Yaklaşımın Detaylı Artıları ve Eksileri

✓ Artıları

  • Audit trail: Event store'da tüm geçmiş. KVKK/SOC2 compliance otomatik.
  • Geri alma: Yanlış onay → compensating event → state düzeltilir.
  • Temporal query: "Bu form 3 gün önce hangi durumdaydı?" → event replay.
  • Test edilebilirlik: Domain layer DB olmadan test edilir. CI'da saniyeler içinde 1000 test.
  • Teknoloji bağımsızlığı: PostgreSQL → başka DB? Sadece adapter değişir.
  • Performans: In-process çağrı (0 latency) + append-only yazma (hızlı) + projection okuma (hızlı).
  • AI için doğal veri: Event stream = pattern mining, anomali, öneri sistemi kaynağı.
  • Scale yolu: Darboğaz modülünü çıkarmak kolay — sınırlar çizili, event'ler hazır.
  • Maliyet: ~$185-350/ay. Full microservice'in %15-25'i.

✗ Eksileri

  • Event sourcing öğrenme: Ekipte ilk kez ise 2-4 hafta yavaşlama. Ama sadece workflow modülünde.
  • Event schema evolution: Event yapısı değiştiğinde eski event'ler okunabilmeli (upcasting).
  • Projection gecikmesi: Event → projection arası ~ms gecikme. "Kaydettim ama listede yok" edge case'i. Çözüm: read-your-own-writes.
  • Core çökerse: Tüm BPM durur. Ama 2+ replica → 1 pod çökse diğeri devam eder (~2-5 sn restart).
  • Hexagonal boilerplate: Her dış bağımlılık için interface + adapter. Başta fazla, büyüdükçe amorti eder.
  • AI eventual consistency: Kullanıcı "öner" deyince sonuç 1-10 sn gecikir. UX'te "düşünüyor..." göstergesi gerekir.
  • Modüler disiplin: Hexagonal kurallarına uyulmazsa spagetti olur. Code review + architecture test gerekir.

5. Tek Container Yapılarda Yatay Ölçekleme (Horizontal Scaling)

SOA veya Modüler Monolit gibi tek container yaklaşımlarda performans artırmak için aynı container'dan birden fazla replica (instance) çalıştırmak mümkündür. Bu bölüm, bunun nasıl yapılacağını, artılarını, eksilerini ve özellikle DB tarafında oluşabilecek çakışmaları analiz eder.

5.1. Yatay Ölçekleme Nasıl Çalışır?

Azure Container Apps veya Kubernetes'te bu yapıyı kurmak çok kolay: replicas: min=2, max=10 ayarı yeterli. Load balancer trafik artınca yeni replica başlatır, azalınca durdurur.

5.2. Yatay Ölçeklemenin Artıları

ArtıAçıklamaEtki

Yüksek erişilebilirlik (HA) 1 replica çökerse diğerleri çalışmaya devam eder Zero-downtime
Rolling deployment Güncelleme sırasında replica'lar sırayla güncellenir — kesinti yok Zero-downtime deploy
Kaynak verimliliği Auto-scale: gece 2 replica, gündüz 8 replica — sadece kullanıldığı kadar öde Maliyet optimizasyonu
Basitlik Aynı kodu çoğaltıyorsun — servis bölme karmaşıklığı yok Operasyonel kolaylık
Fault isolation Memory leak veya crash bir replica'yı etkiler, diğerleri sağlam Daha güvenilir

5.4. Veritabanı Çakışmaları ve Çözümleri

Birden fazla replica tek DB'ye yazarken oluşabilecek en kritik sorunlar ve nasıl önleneceği:

Problem 1: Connection Pool Tükenmesi

❌ Sorun

PostgreSQL varsayılan max_connections = 100. Her Go instance ~20-50 bağlantı açar. 5 replica = 250 bağlantı → DB reddeder.

Sonuç: "too many connections" hatası, tüm replica'lar düşer.

✓ Çözüm: PgBouncer

PgBouncer (connection pooler) replica'lar ile DB arasına konur. 500 gelen bağlantıyı 20-50 gerçek DB bağlantısına multiplexer.

  • Pool mode: transaction (en verimli)
  • Her replica PgBouncer'a bağlanır (DB'ye değil)
  • Azure'da sidecar container olarak çalışır
  • Kaynak: ~30MB RAM, ~0.1 vCPU

Problem 2: Optimistic Concurrency Violation

❌ Sorun

Kullanıcı A "Onayla" tıklar → Replica 1 workflow'u günceller.
Kullanıcı B aynı anda "Reddet" tıklar → Replica 2 aynı workflow'u günceller.
İkisi de version=5'i okudu, ikisi de version=6 yazmaya çalışır.

Sonuç: Biri başarılı, diğeri "conflict" alır — veri bütünlüğü korunur ama kullanıcı hata görür.

✓ Çözüm: Optimistic Locking + Retry

Event store'daki UNIQUE(aggregate_id, version) constraint tam olarak bunu çözer:

  • İlk yazan kazanır (version check)
  • İkinci yazan "conflict" hatası alır
  • Application: event'i tekrar yükle, state güncelle, retry et
  • 3 denemede çözülmezse → kullanıcıya "başka biri güncelledi" göster
-- Event Store'da Optimistic Concurrency Control INSERT INTO workflow.events (aggregate_id, event_type, event_data, version) VALUES ($1, $2, $3, $4) ON CONFLICT (aggregate_id, version) DO NOTHING RETURNING id; -- Eğer RETURNING boş dönerse → conflict var → retry: -- 1. Event'leri tekrar oku (son version'ı al) -- 2. Business logic'i tekrar değerlendir -- 3. Yeni version ile tekrar dene (max 3 retry)

Problem 3: In-Memory Cache Tutarsızlığı

❌ Sorun

Replica 1: Kullanıcı rolünü cache'ler → "Admin".
Admin panelinden rol "Viewer" yapılır → Replica 2 DB'yi günceller.
Replica 1 hala cache'ten "Admin" döner → yetki bypass!

✓ Çözüm: Redis + Cache Invalidation
  • Shared cache: Tüm replica'lar Redis'ten okur/yazar
  • Pub/Sub invalidation: Bir replica güncellediğinde Redis channel'a "invalidate:user:123" gönderir
  • TTL: Her cache entry max 5dk yaşar — worst case 5dk eski
  • Critical data: Auth/permission asla local cache'lenmez — her seferinde Redis veya DB

Problem 4: WebSocket Event Broadcast

❌ Sorun

Kullanıcı A → Replica 1'de WS bağlı.
Kullanıcı B → Replica 2'de form günceller → event oluşur.
Replica 2 "form güncellendi" event'ini push etmek ister ama Kullanıcı A'nın WS'i Replica 1'de!

✓ Çözüm: Redis Pub/Sub Fan-out
  • Event oluştuğunda: Redis channel'a publish et
  • Tüm replica'lar bu channel'ı subscribe eder
  • Her replica kendi bağlı kullanıcılarına push yapar
  • Alternatif: Supabase Realtime veya NATS kullanılabilir

Problem 5: Distributed Cron (Tekrarlı Job'lar)

❌ Sorun

Her gece 03:00'te "raporları oluştur" cron job'u var.
3 replica = 3 kez aynı rapor oluşur → duplikasyon, gereksiz yük.

✓ Çözümler
  • En iyi: Cron job'ları ayrı worker container'a taşı (scale-to-zero) — replica'lardan bağımsız
  • Alternatif: Redis SETNX ile distributed lock — ilk alan çalıştırır, diğerleri skip
  • DB lock: PostgreSQL advisory lock — SELECT pg_try_advisory_lock(job_id)

Önemli Not: DB Yatay Ölçekleme ≠ Container Yatay Ölçekleme

Container'ları çoğaltmak kolay ve ucuzdur. Ama PostgreSQL tek instance kalır — DB'yi yatay ölçeklemek (sharding) çok karmaşıktır ve genelde gereksizdir. Bunun yerine:

  • PgBouncer: Bağlantı sayısını yönet (500 → 50 gerçek conn)
  • Read Replica: Dashboard/report sorgularını replika'ya yönlendir (write = primary, read = replica)
  • Connection-aware auto-scale: Max replica × conn_per_replica < DB max_connections kuralı
  • Dikey ölçekleme (DB tier): 2 vCPU → 4 vCPU → 8 vCPU (çoğu durumda yeterli)

SOA'da container çoğaltabilir miyiz? Evet, çok kolay. Azure Container Apps 1 satır config ile auto-scale yapar.
Performans artışı doğrusal mı? Evet (I/O-bound iş yükleri için). CPU-bound'da DB darboğaz olabilir.
DB çakışmaları olur mu? Evet ama yönetilebilir. Optimistic locking + PgBouncer + Redis ile tüm sorunlar çözülür.
Microservice'e göre avantajı ne? Aynı ölçekleme kapasitesi, ama: 1 codebase, 1 DB, 0 network latency, daha ucuz, daha basit.
Ne zaman yetmez? Bir modül çok farklı kaynak profili gerektiriyorsa (örn: AI → GPU), o modülü ayırırsın (zaten SOA'da AI ayrı system).

Önerilen Yatay Ölçekleme Stratejisi (BPM Tool)

Core BPM: min=2, max=8 replica (HTTP concurrent requests'e göre auto-scale)
AI Service: min=1, max=4 replica (queue depth'e göre auto-scale)
Workers: min=0, max=5 (scale-to-zero, queue depth'e göre)
PgBouncer: Her Core replica'nın sidecar'ı olarak çalışır (veya shared pool)
Redis: Tüm replica'lar arası shared cache + pub/sub + distributed lock
DB: Başlangıçta tek PostgreSQL (2 vCPU). 50+ müşteride read replica ekle.
