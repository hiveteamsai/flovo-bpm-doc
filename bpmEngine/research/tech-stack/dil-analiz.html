5. gRPC Desteği

gRPC, Google'ın geliştirdiği yüksek performanslı RPC (Remote Procedure Call) framework'üdür. HTTP/2 üzerinden Protocol Buffers (protobuf) kullanarak binary serialization yapar. Microservice/SOA mimaride servisler arası iletişim ve mobil client bağlantısı için kritik bir teknolojidir.

5.1. gRPC Neden Önemli (BPM İçin)?

Kullanım AlanıAçıklamaNeden REST Yetmez?
Servisler arası iletişim Core BPM → AI Service, Core → Workers REST JSON: serialize/deserialize yavaş (10-50x fark). gRPC binary = çok hızlı.
Bi-directional streaming Real-time workflow durumu, canlı log akışı REST = request/response. gRPC stream = sürekli veri akışı (WebSocket benzeri ama tip güvenli).
Mobil client Mobil app → Backend bağlantısı gRPC ~7-10x daha az bandwidth kullanır (binary). Mobilde veri tasarrufu.
Code generation .proto dosyasından tüm dillere client/server üretimi OpenAPI benzeri ama derleme zamanında tip kontrolü garanti.

5.3. gRPC — Dil Bazında Artılar ve Eksiler

Go + gRPC
  • Artı: gRPC referans implementasyonu Go'da yazıldı — en iyi performans, en olgun ekosistem
  • Artı: Kubernetes, Istio, Envoy hep Go + gRPC — doğal entegrasyon
  • Artı: protoc-gen-go ile otomatik, tip güvenli server/client kodu
  • Artı: Bidi streaming ile real-time workflow event push
  • Eksi: protobuf dosya yönetimi (buf.build ile çözülür)
.NET 9 + gRPC
  • Artı: ASP.NET Core'da first-class support — Startup'ta 1 satır
  • Artı: gRPC-Web native (browser'dan doğrudan bağlantı)
  • Artı: dotnet-grpc tool ile .proto'dan otomatik C# class üretimi
  • Artı: Deadline, cancellation, metadata desteği native
  • Eksi: AOT build'de bazı reflection-based gRPC kütüphaneleri sorunlu
Python + gRPC
  • Artı: grpcio resmi desteği var, AI servisleri için yeterli
  • Artı: TensorFlow Serving, Triton gibi AI toollar gRPC kullanıyor
  • Eksi: C-binding tabanlı (grpcio) — install sorunları yaygın
  • Eksi: Performans çok düşük (~15-30K req/sec) — Python GIL darboğaz
  • Eksi: async gRPC (grpcio-asyncio) hala bazı stability sorunları var
Node.js / Bun + gRPC
  • Artı: @grpc/grpc-js saf JS implementasyonu — native bağımlılık yok
  • Artı: ts-proto ile güzel TypeScript tipleri üretilir
  • Artı: nice-grpc kütüphanesi developer experience iyileştiriyor
  • Eksi: Performans Go/C#'a göre 5-7x yavaş
  • Eksi: Bun'da gRPC desteği tam olgunlaşmamış (Node compat layer)
  • Eksi: Streaming'de memory leak raporları (yoğun kullanımda)

BPM Tool İçin Önerilen gRPC Stratejisi

Dış dünya (frontend, 3rd party): REST + OpenAPI (kolay entegrasyon, browser uyumlu).
Servisler arası (Core → AI, Core → Worker): gRPC (hızlı, tip güvenli, streaming).
Mobil client: gRPC-Web veya Connect (protobuf ile hızlı, az bandwidth).
Bu hybrid yaklaşım en iyi sonucu verir. Go bu stratejide en doğal şekilde çalışır çünkü hem REST (Fiber/Chi) hem gRPC (google.golang.org/grpc) ekosistemi çok olgun.

6.4. BPM Tool İçin ORM Stratejisi Önerisi

Go İçin: sqlc + pgx (Önerilen)
  • SQL yaz → Go kodu otomatik üretilir (compile-time güvenlik)
  • Native SQL hızı — ORM overhead yok
  • pgxpool ile built-in connection pooling
  • COPY komutu ile event store'a ultra-hızlı batch insert
  • JSONB sorgulama = native PostgreSQL syntax
  • Migration: golang-migrate ile (basit, güvenilir)

Dezavantaj: SQL elle yazılır (autocomplete yok), ilişki yönetimi manuel. Ama BPM gibi kompleks query'lerde bu avantaja dönüşür — tam kontrol.

TS İçin: Drizzle ORM (Önerilen)
  • Type-safe query builder — SQL'e çok yakın syntax
  • Thin layer = minimal overhead (Prisma'nın Rust engine'ı yok)
  • JSONB operators ile doğrudan çalışır
  • drizzle-kit ile migration
  • Prisma'dan 3x daha hızlı (engine overhead yok)
  • Join desteği iyi — N+1 koruması

Dezavantaj: Henüz genç (2023), bazı edge case'lerde dokümantasyon eksik. Ama aktif geliştirme devam ediyor.

Mevcut .NET Deneyiminizden Ders

Mevcut projenizdeki DefaultFlvService.cs dosyasında EF Core ile Include().ThenInclude() zincirleri var. Bu N+1 query sorununa ve performans problemlerine yol açar. Yeni projede sqlc (Go) veya Drizzle (TS) seçerseniz, SQL'i doğrudan kontrol ettiğiniz için bu tür sorunlarla karşılaşmazsınız — her query tam olarak ne ürettiğini bilirsiniz.

Patron'a Söylenecekler

Eğer Patron JS'te ısrar ederse:
  • Bun + Hono orta yol olabilir
  • Go'ya yakın performans (~250K req/sec)
  • TypeScript tip güvenliği
  • JS ekosistemi erişimi
  • Ama: CPU-heavy iş (rule engine) yavaş olacak
  • Ama: Bun henüz çok genç (production risk)
Neden Go daha iyi:
  • Yılda $600-1500 RAM tasarrufu
  • 3-4x daha hızlı API response
  • Workflow/concurrency için doğal (Goroutines)
  • Temporal (en iyi workflow engine) Go ile yazılmış
  • OpenAPI ile frontend aynı tip güvenliğini alır
  • "Aynı dil" avantajının %100'ü dil bağımsız sağlanır

Pragmatik Karar Çerçevesi

Eğer ekipte Go bilen/öğrenmeye istekli en az 1 kişi varsa → Go
Eğer ekip sadece JS/TS biliyorsa ve öğrenmeye zaman yoksa → Bun + Hono
Eğer mevcut .NET bilgisi değerlendirilmek isteniyorsa → .NET 9 Minimal API + AOT
Her durumda AI Service → Python (alternatifi yok)
