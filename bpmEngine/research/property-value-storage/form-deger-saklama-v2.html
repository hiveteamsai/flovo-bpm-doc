Benzetme (tüm sunum için tek metafor): Bir form kaydı = bir klasör. Klasörün içindeki belgeler = alan değerleri. Tapu senedi (InstanceValue) klasörün asıl içeriğidir. Fihrist / kartotek (InstanceAttr, InstanceListItem) “şu tutardan büyükleri bul” diye hızlı arama için çıkarılmış kopya kartlardır. Kartlar yanarsa tapudan yeniden basılır. Tapu yanarsa felaket — onu koruruz.

1 Problem — neden “sadece bir tablo” yetmez?

Flovo’da her müşteri (organizasyon) kendi formlarını Form Designer ile tasarlar. Bir masraf formunda 20 alan olabilir; başka bir müşteride aynı “Masraf” 100+ alan olabilir. Üstelik alanlar canlıda eklenir, gizlenir, tipi değişir.

Müşteri A — Masraf

20 alan: tutar, şirket, fatura no, tarih, açıklama…

Müşteri B — Masraf

100+ alan: proje kodu, 5 vergi alanı, onay notları, groupByTax kalem listesi, ek dosyalar…

Aynı anda sistem şunları da ister:

  • Hızlı form açma — kullanıcı kaydettiği formu hemen görsün.
  • Hızlı rapor / arama / sıralama / toplam — “tutarı 5000’den büyük onay bekleyenler”.
  • Şema değişince migration cehennemi olmasın — her alan eklemede ALTER TABLE yok.
  • Bozulunca toparlanabilsin — projeksiyon yanlış olsa bile asıl veri kaybolmasın.
  • Audit / KVKK — kim neyi ne zaman değiştirdi kanıtlanabilsin.

2 Dört temel kavram — karıştırma!

Junior’ların en sık yaptığı hata: “form”, “alan”, “değer”, “liste” kelimelerini birbirinin yerine kullanmak. Bu dört kavram ayrı tablolarda / ayrı yaşam döngüsünde yaşar.

1) Property (alan tanımı)

Ne: Designer’da çizilen alan. “Bu serviste amount adında sayısal bir alan var.”

Nerede: Servis ayarları — Property tablosu.

Örnek alanlar: code, definition (görünen ad), controlTypeId, projectToAttr (bool).

Değişmez kural: code teknik kimliktir (sonra anlatıyoruz).

2) Instance (doldurulmuş form)

Ne: Kullanıcının açtığı / sürecin ürettiği tek bir form kaydı.

Nerede: Instance — kimlik, durum, oluşturan, soft-delete.

Önemli: Instance değerleri taşımaz. “Bu form onay bekliyor” bilgisi burada; “tutar=1800” burada değil.

Örnek: Masraf #45821, status=Onay Bekliyor, creator=Ayşe.

3) InstanceValue (değerlerin tapusu)

Ne: O Instance’ın tüm alan değerleri tek JSONB kutuda.

Nerede: InstanceValue — Instance ile 1–1.

Örnek data:

{
  "amount": 1800,
  "expenseType": "2",
  "barcode": "8690…",
  "groupByTax": [
    {"giderTuru":"yemek","vergiOrani":18,"tutar":1000},
    {"giderTuru":"ulasim","vergiOrani":8,"tutar":800}
  ],
  "receipt": "minio://org/…/fatura.pdf"
}

4) Projection (fihrist / kartotek)

Ne: Rapor-arama için JSONB’den türetilmiş tablolar.

Nerede: InstanceAttr (skaler alanlar) · InstanceListItem (liste kalemleri).

Kritik: Bunlar kaynak değil. Silinseler bile InstanceValue’dan yeniden üretilir.

Ne zaman kullanılır: Liste, filtre, sıralama, toplam — asla tek form detay ekranı için değil.

Ek ayrım — Service / ProcessInstance:
  • Service = form tipi tanımı (Masraf Servisi). Property’ler buraya bağlıdır.
  • ProcessInstance = iş akışı çalışması. Bir ProcessInstance bir veya daha çok Instance üretebilir.
  • eventForm tipinde servis → Instance oluşmaz; değerler geçici parameters ile taşınır (kalıcı değer saklama yok).

3 Mimari sözleşme — 3 cümle, asla bozulmaz

1 — Bu sistem Event Sourcing DEĞİLDİR. Olaylardan formu yeniden kurmayız. Olaylar sadece projeksiyonu beslemek için taşıma aracıdır.

2 — Tek gerçek kaynak = InstanceValue.data (JSONB). Nokta. Kullanıcı formunu buradan görür.

3 — InstanceAttr, InstanceListItem, rollup’lar projection’dır: bugün silinseler, yarın kaynakdan bit-bit aynı üretilir. İçlerinde “başka yerde olmayan” bilgi yoktur.

Benzetme: Tapu senedi vs fotokopi. Fotokopiyi optimize edebilir, yırtıp yeniden basabilirsin. Tapuyu kaybedersen mahkeme gerekir.
Pratik sonuçlar:
  • Detay ekranı asla projeksiyona bakmaz → projection lag formu bozamaz.
  • Projeksiyon birkaç yüz ms bayat olabilir (eventual consistency) — rapor tarafında kabul.
  • Yedeklemede asıl korunan: Instance + InstanceValue + Property metadata.

Aşağıdaki tablolar değer saklama mimarisinin tam listesidir. Junior: önce isimleri ezberle, sonra alanları.

6.1 Instance (zaten var — değer tutmaz)

Doldurulmuş formun kimlik ve durum kaydı. Sık değişen küçük alanlar burada kalır; JSONB’ye gömülmez.

6.2 InstanceValue — kaynak hakikat (tapu)

Instance ile 1–1. Büyük/seyrek-churn veri burada; status gibi sık-churn Instance’da.

AlanTipNe işe yarar
instanceIdPK / FK → InstanceHangi form
organizationIdintKiracı (RLS)
serviceIdintPartition + sorgu pruning
datajsonbTüm alan değerleri — code-keyed

createdAt / updatedAttimestamptzİzleme
 
CREATE TABLE instance_value (
  instance_id      bigint PRIMARY KEY REFERENCES instance(id),
  organization_id  int NOT NULL,
  service_id       int NOT NULL,
  data             jsonb NOT NULL,
  version          int NOT NULL DEFAULT 1,
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_at       timestamptz NOT NULL DEFAULT now()
) PARTITION BY HASH (service_id);

CREATE INDEX ix_iv_data ON instance_value USING gin (data jsonb_path_ops);
code-keyed ne demek? JSON anahtarları Property.id değil, Property.code’dur: {"amount":1800} — API, iş kuralı, custom code aynı dili konuşur.

Klasik EAV ile fark: Klasik EAV’de fihrist = tek gerçek → form açmak 100 satır pivot + tip kaybı. Bizde fihrist silinse bile tapu durur; tipler ayrı kolonlarda (9 < 10 doğru).

8 Yazma yolu — adım adım (kullanıcı kaydetti)

Senaryo: Ayşe masraf formunda tutarı 1500 → 1800 yaptı ve kaydetti.

Adım 1 — İstek gelir

Frontend veya motor changeList / PATCH gönderir: { amount: 1800 } (+ diğer alanlar partial veya full).

Adım 2 — Kapıda JSON Schema doğrulama

Designer yayınından üretilen şema: amount number olmalı, expenseType bilinen kodlardan biri…

amount: "abc" → red, DB’ye hiç yazılmaz. Projektöre çöp sızmaz.

Adım 3 — Snapshot yansımalar (gerekirse)

Yeni kayıt ise UserInfo alanları (departman, unvan) şimdi JSONB’ye kopyalanır ve dondurulur.

ParentProperty reflectionMode=snapshot ise parent’tan değer çekilip yazılır.

Adım 4 — Tek atomik transaction

  UPDATE instance_value
     SET data = :yeni_jsonb,
         version = version + 1,

   WHERE instance_id = 45821;

  INSERT INTO instance_value_outbox
    (event_id, instance_id, service_id, organization_id, version, occurred_at)
  VALUES (...);

  -- saveChangeLog=true alanlar için:
  INSERT INTO instance_value_change (...);

Commit anında kullanıcı kendi formunu anında doğru görür (JSONB güncel). Projeksiyon henüz eski olabilir — sorun değil, detay Attr’a bakmaz.

Adım 5 — Arka plan (kullanıcı beklemez)

Outbox relay → NATS JetStream → Generic projektör (aşağıda §18–19).

Yazmanın dürüst maliyeti

9 Okuma yolları — hangi sorgu nereye gider?

Altın kural: Detay = JSONB · Arama/sıra/aralık = Attr · Kalem = ListItem

9.1 Detay — formu aç

SELECT i.*, v.data, v.version
FROM instance i
JOIN instance_value v ON v.instance_id = i.id
WHERE i.id = 45821;
  • Pivot yok, Attr yok.
  • Etiketli seçim: LabeledValue (value/display/translationCode) JSONB’den gelir; EN UI gerekirse Translation ile çözer.
  • Canlı yansıma (status): i.statusId kolonundan.
  • Dosya: URL’den MinIO render.

9.2 Eşittir / içerir — GIN

SELECT instance_id FROM instance_value
WHERE service_id = 42
  AND data @> '{"barcode":"8690123456789"}';
Tek GIN, herhangi alanda eşittir. Yeni alan eklemek yeni index istemez. Attr’a yansıtılmamış alan bile bulunabilir!

9.3 Aralık / sıralama — InstanceAttr

SELECT instance_id FROM instance_attr
WHERE service_id = 42
  AND property_code = 'amount'
  AND num_value > 1000
ORDER BY num_value DESC
LIMIT 50;

9.4 Kalem bazlı rapor — InstanceListItem

SELECT instance_id, item_index, num_value AS vergi_orani
FROM instance_list_item
WHERE service_id = 42
  AND list_code = 'groupByTax'

20 Generic projektör — alan adı koda gömülü değil

olay geldi (instanceId, serviceId, version):
  meta = property_cache[serviceId]  # code + tip + projectToAttr
  if version <= projection.last_version: skip
  bu instance’ın InstanceAttr / InstanceListItem satırlarını SIL
  for (code, value) in InstanceValue.data:
    prop = meta[code]
    if !prop.projectToAttr: continue
    if prop is list-of-model:
      her kalem/alt-alan → InstanceListItem
    else:
      tip kolonuna yaz → InstanceAttr
  last_version = version
Yeni servis / yeni alan için projektör kodu değişmez. Sadece Property metadata. Bu mimarinin ölçeklenebilirliğinin kalbi.
Not: metadataVersion kullanılmıyor. Projektör güncel Property tanımına göre yansıtır. Alan tipi kökten değişirse bilinçli rebuild / migrasyon gerekir.

26 SSS — junior’ın sık sorduğu 20 soru

1) Formu açarken InstanceAttr’a mı bakıyorum?

Hayır. Detay = Instance + InstanceValue. Attr yalnız liste/rapor/arama içindir. Attr bayat olsa bile formu doğru görürsün.

2) Neden her alanı Attr’a yazmıyoruz?

Satır patlaması + her kayıtta daha çok yazma. %10–20’si yeter. Gerisi JSONB’de; eşittir sorusu GIN ile yine çalışır.

3) Yeni alan ekleyince migration yazar mıyım?

Hayır. Property satırı + projectToAttr. DDL yok. Eski kayıtlarda anahtar yoktur (= boş).

4) Alanı silince geçmiş veriler uçar mı?

Varsayılan soft retire: JSONB’de orphan anahtar kalır. Hard purge ayrı KVKK/job kararıdır.

5) Combobox’ta isim mi kod mu saklanır?

Kod. İsim dile bağlı ve değişebilir. Ekranda Translation ile çözülür.

6) “Tutar’ı Amount yap” diye code değiştirir miyiz?

Hayır. Etiketi (definition/çeviri) değiştirirsin. code kilitlidir.

7) Status neden JSONB’de değil?

Sürekli değişir. JSONB’de olsa her onayda tüm kutu yeniden yazılır + rapor bayatlar. Instance.statusId kolonu hem canlı hem indeksli.

8) Projeksiyon 2 sn gecikirse kullanıcı ne görür?

Kendi formu: anında doğru (JSONB). Liste/rapor: 2 sn eski olabilir → eventual consistency, alarm eşiği izlenir.

9) Outbox ile NATS aynı şey mi?

Hayır. Outbox = DB’de “henüz yayınlanmadı” kaydı (TX ile atomik). NATS = kalıcı kuyruk. Relay outbox’tan NATS’a taşır.

10) Event sourcing mi bu?

Değil. Formu olaylardan kurmayız. Olay sadece fihristi besler. Tapu JSONB’dir.

11) groupByTax ile Form List aynı mı?

Değil. groupByTax = aynı JSON içinde dizi → ListItem. Form List = ayrı child Instance’lar → RelatedInstance.

12) PDF’i JSONB’ye koyabilir miyiz?

Teknik olarak mümkün, mimari olarak yasak. MinIO’ya koy, JSONB’de URL tut. Aksi halde yazma maliyeti patlar.

13) 150 property sorun mu?

Alan sayısı değil bayt × update sıklığı sorun. Tipik 15–40 KB yönetilebilir. Büyük metin/binary MinIO’da.

14) Attr’da property_id mi property_code mu?

property_code. Kaynak JSONB code-keyed; API aynı dili konuşur; join’siz; FK yükü yok.

15) Parent değişince child otomatik güncellenir mi?

Varsayılan hayır (snapshot). Canlı için B; canlı+ağır rapor için A′ (ReflectionLink) — Designer’da bilinçli seçim.

16) İş kuralı (frontend) Attr’a bakar mı?

Hayır. Bellekteki form değerleri üzerinde çalışır. Kalıcılık kaydet ile JSONB’ye düşer.

17) Motor switch/karşılaştırma nereden okur?

Tek instance için JSONB (veya belleğe yüklenmiş data). Çok-kayıt arama değil.

18) Projection bozulursa veri kaybı mı?

Hayır — rebuild. Kaybı yalnız InstanceValue kaybı yaratır → yedek/PITR.

19) Eski araştırmadaki form_value / form_attr ne?

Aynı şeyin eski adı. Flovo model dilinde: InstanceValue / InstanceAttr / InstanceListItem.

20) Bu karar todo’da kapandı mı?

Henüz 🟡. Bu sunum önerilen mimari. Ürün onayı sonrası models/ + todo [x].

27 Uçtan uca örnek — Masraf formu (hikâye)

Ayşe bir masraf oluşturuyor. Her adımda hangi tabloya ne yazıldığını izleyelim.

T0 — Servis tasarımı (çoktan yapılmış)

Service “Masraf”, Property’ler: amount (projectToAttr=true), expenseType (true, LabeledValue), groupByTax (liste), receipt (false+MinIO), note (false), creatorDept (userInfo snapshot).

T1 — Instance Creator adımı çalışır

ProcessInstance + Instance (status=Taslak, creator=Ayşe, createdDate=şimdi).

InstanceValue oluşur: data ≈ defaults + creatorDept: "Satınalma" (snapshot).

Aynı TX’de outbox. Projektör az sonra projectToAttr=true alanları Attr’a yazar (LabeledValue ise display dahil).

T2 — Ayşe formu doldurur

amount=1500, expenseType="2", groupByTax’a 2 kalem, receipt yükler → MinIO URL.

Kaydet → validate → InstanceValue.data güncellenir, version=2, outbox.

Ayşe ekranda anında 1500 görür.

T3 — Projektör (~200ms sonra)

Attr: amount=1500, expenseType="2", …

ListItem: 2 kalem × (giderTuru, vergiOrani, tutar).

Rapor artık bu tutarı filtreleyebilir.

T4 — Ayşe tutarı 1800 yapar (saveAndRefresh)

version=3. Attr yeniden tam yansıtılır (delta değil). ListItem aynı kalırsa yine sil+yaz (basit ve güvenli).

T5 — Onaya gönder

Motor: statusId → Onay Bekliyor (Instance kolonu). Belki note changeList ile yazılır.

InstanceAwaitingUser oluşur (değer tablosu değil).

T6 — Yönetici rapor ister: “tutarı > 1000 onay bekleyenler”

Instance.statusId filtresi + InstanceAttr amount > 1000. JSONB taranmaz.

T7 — Designer’a projectCode eklenir

Property yeni. Ayşe’nin kaydında projectCode yok → boş. Yeni masraflarda dolacak. DDL yok.

T8 — Finance “note alanına göre arama” ister

note projectToAttr=false idi → true yapılır → bulk rebuild → eski kayıtlardaki note’lar Attr’a düşer. Yeni index yok.

Bu hikâye mimarinin tamamını özetler: tapu anında doğru, fihrist biraz gecikmeli ama rebuild edilebilir, şema değişimi metadata işi, status ayrı, dosya dışarıda.

28 Tek sayfalık özet — duvara asılacak sözleşme

1. Tapu = InstanceValue.data (JSONB, code-keyed).

2. Fihrist = InstanceAttr + InstanceListItem (yeniden üretilebilir).

3. Detay ekranı fihriste bakmaz. Rapor detaya (pivot cehennemine) mahkûm değildir.

4. Yazma: validate → Value + Outbox (aynı TX) → NATS → idempotent tam-yansıtma.

5. Status / creator / createdDate = Instance kolonları. Dosya = MinIO URL.

6. Alan ekle/sil = metadata (+ rebuild), DDL değil.

7. code dondurulur; etiket serbest. projectToAttr (bool) fihrist büyümesini kısıtlar. metadataVersion yok.

8. Yansıma: değişmez→snapshot · değişen gösterim→canlı · değişen+ağır rapor→A′.

9. Etiketli seçimde LabeledValue: kod+display(+translationCode). Raporda isim → Attr.display.

10. Fihrist yanarsa rebuild. Tapu yanarsa felaket — onu yedekle.
